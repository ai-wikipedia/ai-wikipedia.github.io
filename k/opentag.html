OpenTag

OpenTag은 Slack이나 Microsoft Teams 채널에서 AI를 멘션해 일을 맡기면 같은 스레드에 결과를 돌려주는 'AI 동료'형 에이전트다. Claude Tag와 인터페이스는 같지만 특정 모델 회사에 묶이지 않는 게 특징이다. 작업마다 맞는 모델을 고르거나 자기 서버에서 직접 운영할 수 있어서 쓴다.

채팅방에서 동료를 부르듯 AI를 부르는 방식

OpenTag은 팀 메신저 안에서 AI를 '태그'해 일을 맡기는 에이전트다. Slack 채널에서 사람 동료에게 "@누구 이것 좀 봐줘"라고 하듯 AI를 멘션해서 작업을 넘기면, AI가 처리한 결과가 같은 스레드에 올라온다. 그래서 팀원 모두가 결과를 함께 볼 수 있다. 이 방식은 Anthropic의 Claude Tag가 먼저 대중화했다. OpenTag을 만든 쪽은 인터페이스는 그게 맞다고 인정하면서도, 여러 사람이 함께 쓰는 이 '멀티플레이어 하네스'가 특정 모델 회사 소유여서는 안 된다고 본다. 이들이 내세우는 핵심이 모델 애그노스틱이다. 더 좋은 모델이 나오면 그날 바로 갈아 끼워서 성능과 비용 개선을 그대로 누리자는 것이다.

이름이 같은 다른 프로젝트도 많다. 마이크로컨트롤러용 DASH7 프로토콜 스택, 2005~2008년 MIT 미디어랩의 RFID 플랫폼, iGaming 플랫폼, 3D 프린터 필라멘트용 NFC 태그 포맷이 모두 OpenTag이라는 이름을 쓴다. AI 맥락에서 OpenTag이라고 하면 보통 2026년 6월 무렵 나온 'Slack 속 AI 동료' 계열을 가리키고, 지금은 성격이 다른 세 갈래 구현이 있다.

세 가지 OpenTag, 각자 다른 쓰임새

첫째는 Y Combinator 지원을 받은 같은 이름의 SaaS다. Slack이나 Teams에 추가해 원하는 채널에 초대하면, 회사가 어떻게 굴러가는지, 결정은 어떻게 내리는지, 누가 무엇을 맡는지를 익혀 간다. 작업을 태그하면 80개 이상의 모델 가운데 그 일에 맞는 모델로 라우팅한다. 반복되는 업무가 눈에 띄면 "매주 월요일 9시에 이걸 돌릴까요?" 같은 자동화를 먼저 제안한다. 일하면서 회사의 실제 운영 방식을 위키로 정리해 두기 때문에, 시간이 갈수록 맥락이 쌓이는 구조다. 실행은 클라우드의 전용 머신에서 일어난다. 실행마다 샌드박스가 따로 만들어지고, 사용자가 연결한 도구 범위 안에서만 움직이며, 작업이 끝나면 정리된다.

둘째는 CopilotKit이 공개한 오픈소스 CopilotKit/OpenTag다. AG-UI 에이전트를 Slack과 Teams로 끌어오는 Channels SDK의 스타터 앱이고, LangGraph로 만든 셀프 호스팅 온콜 트리아지 봇 형태다. 처음부터 포크해서 고쳐 쓰라고 만든 앱이라, 바꾸고 싶은 부분이 파일 하나나 디렉터리 하나에 모여 있고 Channel 생명주기 코드는 건드리지 않아도 된다. 외부 연동을 하나도 붙이지 않아도 대화, 지식 작업, 모델 지식 기반 UI 렌더링은 된다. 사내 장애 대응 봇을 처음부터 짜기보다 이걸 출발점으로 삼아 자기 도구만 끼우면 된다.

셋째는 MIT 라이선스의 amplifthq/opentag로, 개발팀 쪽에 초점을 둔다. Slack, GitHub, GitLab, Linear, Lark에서 멘션하면 ACP를 지원하는 코딩 에이전트(Claude Code, Codex, Cursor 등)를 내가 관리하는 컴퓨터에서 실행한다. 셀프 호스팅 Control Plane이 요청을 받아 큐에 쌓아 두기 때문에, 연결된 컴퓨터가 꺼져 있어도 멘션은 받는다. Runner가 준비되면 로컬 체크아웃을 대상으로 에이전트를 돌리고, 진행 상태와 판단 내용, 근거를 같은 스레드에 보고한다. 예를 들어 Linear 이슈 스레드에서 에이전트를 부르면 내 노트북의 저장소에서 수정 작업이 진행되고, 결과는 스레드로 돌아온다.

권한과 신뢰를 어디까지 열어 줄 것인가

채팅방에서 AI를 부르는 건 편하지만, 그만큼 누가 무엇을 바꿀 수 있는지가 흐려지기 쉽다. amplifthq 구현은 이 지점을 명시적으로 다룬다. 실행기 출력, 실행 상태, GitHub 게시, 메신저 전달을 각각 따로 증거를 남기는 별개의 사실로 보고한다. 드래프트 PR 게시도 따로 통제되는 단계로 분리해 두었다. 자동 머지는 하지 않고, 채팅에 적힌 문장만으로 접근 권한이 넓어지지 않게 막는다. SaaS판이 실행마다 샌드박스를 만들고 연결된 도구 범위로 권한을 묶는 것도 같은 고민에서 나온 설계다.

트레이드오프도 분명하다. SaaS판은 바로 쓸 수 있고 모델 라우팅으로 비용을 낮출 수 있지만, 회사 맥락과 위키가 외부 서비스에 쌓인다. 오픈소스 두 갈래는 코드와 실행 환경을 직접 쥘 수 있는 대신 배포와 운영을 스스로 맡아야 한다. 결국 고를 기준은 하나다. 팀이 AI 동료에게 기대하는 게 업무 자동화인지, 장애 트리아지인지, 실제 코드 수정인지에 따라 맞는 구현이 달라진다.
