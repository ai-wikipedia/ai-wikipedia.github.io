KV 캐시

KV Cache

트랜스포머가 토큰을 생성할 때마다 이전 계산 결과를 재사용할 수 있도록 저장해두는 캐시. 반복 계산을 줄여 추론 속도를 크게 높인다.

이미 읽은 부분을 다시 계산하지 않기

KV 캐시(KV Cache)란 트랜스포머 모델이 글을 생성하는 동안, 앞서 처리한 토큰들의 계산 결과 중 Key와 Value를 메모리에 저장해 두고 재사용하는 장치다. LLM은 답을 한 토큰씩 쓰고, 새 토큰을 하나 만들 때마다 지금까지의 모든 토큰을 참고한다. 캐시가 없다면 100번째 토큰을 만들 때 앞의 99개를 처음부터 다시 계산하고, 101번째에서 또 100개를 다시 계산해야 한다. 소설을 한 문장 쓸 때마다 1장부터 다시 읽는 작가와 같다. KV 캐시는 이미 읽은 부분에 대한 메모를 옆에 두고 새 문장만 추가로 읽는 방식이다.

왜 하필 Key와 Value일까. 어텐션은 현재 토큰의 Query를 이전 모든 토큰의 Key와 비교해 어디에 주목할지 정하고, 그 비율대로 Value를 섞는다. 이전 토큰들의 Key와 Value는 뒤에 무엇이 오든 바뀌지 않지만, Query는 지금 만드는 토큰에만 필요하다. 그래서 K와 V만 레이어마다 쌓아 두면 된다. vLLM 논문의 계산으로는 OPT-13B 모델에서 토큰 하나당 KV 캐시가 약 800KB(Key와 Value 2개 × 은닉 차원 5,120 × 레이어 40개 × FP16 2바이트)에 이른다.

첫 토큰은 느리고 그다음은 빠른 이유

추론은 두 단계로 나뉜다. 프롬프트 전체를 한꺼번에 처리해 KV 캐시를 채우는 프리필과, 캐시를 읽으며 토큰을 하나씩 만드는 디코드다. 긴 문서를 넣으면 첫 글자가 나오기까지 한참 걸리고(TTFT, 첫 토큰까지의 시간) 그다음부터 술술 나오는 건 이 구조 때문이다. 프리필은 많은 토큰을 병렬로 처리해 GPU 연산력을 많이 쓰고, 디코드는 토큰 하나를 만들 때마다 거대한 캐시를 메모리에서 읽어 와야 해서 메모리 대역폭에 묶인다. Hugging Face 블로그의 실험에서는 SmolLM2-1.7B 모델로 토큰 300개를 생성할 때 KV 캐시를 쓰면 11.7초, 끄면 1분 1초가 걸려 약 5배 차이가 났다.

속도의 대가는 메모리

문제는 캐시가 크다는 것이다. 크기는 토큰 수, 레이어 수, 어텐션 헤드 크기에 비례해 커지고, 동시 사용자마다 따로 필요하다. vLLM 팀에 따르면 LLaMA-13B 한 요청의 KV 캐시가 최대 1.7GB에 이른다. GPU 메모리에서 모델 가중치를 빼고 남은 공간이 곧 KV 캐시 자리이고, 이 자리가 한 번에 처리할 수 있는 요청 수를 결정한다. 그런데 기존 서빙 시스템은 요청마다 최대 길이만큼 연속된 메모리를 미리 잡아 두는 방식이라 KV 캐시 메모리의 60~80%를 낭비하고 있었다.

2023년 vLLM의 PagedAttention은 운영체제의 가상 메모리 페이징을 빌려 이 문제를 풀었다. KV 캐시를 작은 블록으로 나눠 필요할 때마다 할당하고, 블록 테이블로 흩어진 블록들을 논리적으로 이어 붙인다. 낭비는 마지막 블록에서만 생겨 4% 미만으로 줄었고, 처리량은 기존 시스템 대비 2~4배 올랐다. 모델 구조 쪽에서도 캐시를 줄이는 시도가 이어진다. 여러 Query 헤드가 Key·Value 헤드를 나눠 쓰는 GQA는 최신 오픈 모델에서 흔한 설계가 됐고, Apple의 온디바이스 모델은 뒤쪽 레이어가 앞쪽 레이어의 KV 캐시를 재사용하게 해 캐시 메모리를 37.5% 줄였다. 캐시를 FP8 같은 낮은 정밀도로 저장하는 양자화도 널리 쓰인다.

API 요금표에서 만나는 KV 캐시

개발자가 KV 캐시를 가장 직접 체감하는 곳은 프롬프트 캐싱이다. 같은 시스템 프롬프트, 도구 정의, 긴 문서로 시작하는 요청이 반복되면, 그 앞부분의 KV 캐시를 서버에 보관해 두고 다음 요청에서 프리필을 건너뛰는 것이다. Anthropic API에서는 cache_control로 캐시 지점을 표시하며, 기본 수명은 5분(쓸 때마다 연장)이고 1시간 옵션도 있다. 캐시에 쓸 때는 기본 입력 가격보다 조금 더 내지만, 캐시에서 읽은 입력 토큰은 기본 가격의 10% 이하로 과금된다.

캐시는 tools, system, messages 순서로 이어지는 접두사가 정확히 일치해야 적중한다. 그래서 바뀌지 않는 내용을 앞에 두고 매번 달라지는 내용은 뒤로 보내야 한다. 시스템 프롬프트 맨 앞에 현재 시각을 넣는 습관이 캐시를 매번 깨뜨리는 대표적인 실수다. 수백 턴 이어지는 코딩 에이전트 세션이 감당할 만한 비용으로 돌아가는 것도 앞선 대화의 캐시를 계속 재사용하기 때문이다. vLLM 같은 자체 서빙 엔진도 같은 접두사를 가진 요청끼리 KV 블록을 공유하는 프리픽스 캐싱을 지원한다.
