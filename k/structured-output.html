구조화된 출력

Structured Output

AI가 JSON 스키마 같은 정해진 형식을 100% 지켜서 응답하도록 강제하는 기술. AI를 기존 코드 파이프라인에 안정적으로 연결하기 위한 핵심 요소다.

'JSON으로 줘'가 늘 지켜지지는 않던 문제

구조화된 출력(Structured Output)이란 LLM의 응답이 개발자가 지정한 JSON 스키마를 반드시 따르도록 강제하는 기능이다. LLM은 원래 자유로운 문장을 쓰도록 만들어졌다. 그래서 "결과를 JSON으로만 답해"라고 부탁해도 앞에 "네, 요청하신 결과입니다"라는 인사를 붙이거나, 코드 블록 기호로 감싸거나, 필수 필드를 빠뜨리거나, 숫자 자리에 "약 3만 원" 같은 문자열을 넣는 일이 생긴다. 사람이 읽을 때는 사소하지만, 그 출력을 JSON.parse()로 받아 DB에 넣는 코드 입장에서는 장애다. 개발자들은 오랫동안 정규식으로 JSON을 뜯어내고, 파싱이 실패하면 다시 요청하는 방어 코드를 짜야 했다.

부탁에서 강제로 바뀐 원리

해결책은 단계적으로 발전했다. 처음엔 프롬프트로 부탁하는 수준이었고, 다음으로 문법적으로 올바른 JSON만 보장하는 JSON 모드가 나왔다. 하지만 JSON 모드는 어떤 키가 있어야 하는지까지는 지켜 주지 않았다. 지금의 구조화된 출력은 제약 디코딩으로 스키마 준수 자체를 보장한다. 스키마를 일종의 문법으로 컴파일해 두고, 모델이 토큰을 하나씩 고를 때마다 그 문법을 깨뜨리는 후보는 선택지에서 아예 지워 버리는 방식이다. 숫자가 와야 하는 자리에서는 숫자로 시작하는 토큰만 남고, 닫는 중괄호가 와야 할 때는 다른 길이 없다. 모델의 '실수할 자유'를 생성 단계에서 없애는 셈이다. 그래서 문법을 컴파일해야 하는 첫 요청은 조금 느리고, 이후에는 캐시된 문법을 재사용한다. Anthropic은 컴파일된 문법을 마지막 사용 후 24시간 동안 보관한다.

API에서 켜는 방법

OpenAI는 Responses API의 text.format에 type: "json_schema"와 strict: true를 넣어 켜고, 공식 SDK는 파이썬 Pydantic 모델이나 TypeScript Zod 스키마를 그대로 받아 준다. Anthropic은 응답 형식을 정하는 output_config.format(JSON 출력)과 도구 호출 인자를 스키마에 맞게 보장하는 strict: true(엄격한 도구 사용)를 따로 제공한다. 앞의 것은 모델이 '무엇을 말하는지'를, 뒤의 것은 '함수를 어떻게 부르는지'를 고정하는 장치라 에이전트에서는 둘을 함께 쓰기도 한다. vLLM 같은 오픈소스 서빙 엔진에서도 같은 원리의 제약 디코딩을 쓸 수 있고, Apple의 Foundation Models 프레임워크는 Swift 구조체에 @Generable만 붙이면 기기 안 모델이 그 타입 그대로 답을 돌려준다.

쓰임새는 'LLM 출력을 사람이 아니라 코드가 받는 모든 곳'이다. 영수증 사진에서 상호·날짜·금액을 뽑아 회계 시스템에 넣을 때, 문의를 정해진 카테고리 enum 중 하나로 분류할 때, 한 에이전트의 결과를 다음 에이전트에 넘길 때 스키마를 먼저 정의하고 그 타입으로 결과를 받는 '스키마 우선' 방식이 표준이 됐다. 파이썬이라면 Invoice 같은 Pydantic 클래스를 정의해 SDK의 파싱 헬퍼에 넘기면 응답이 곧바로 그 클래스의 객체로 돌아와, 필드 이름 오타를 잡거나 타입을 변환하는 코드를 따로 짤 필요가 없다.

형식이 맞아도 남는 함정

스키마를 지킨다는 것이 내용이 맞다는 뜻은 아니다. 금액 필드에 숫자가 들어가는 건 보장되지만, 그 숫자가 영수증에 적힌 값인지는 따로 검증해야 한다. 형식이 깨지는 예외도 남아 있다. 모델이 안전상 이유로 거절하면(stop_reason: "refusal") 거절 메시지가 스키마보다 우선하고, max_tokens에 걸려 잘리면 JSON이 중간에 끊긴다. 최솟값이나 길이 제한처럼 지원하지 않는 스키마 키워드는 SDK가 지우고 설명문으로 옮기기도 하니, 이런 제약은 응답을 받은 뒤 코드에서 다시 확인해야 한다. Claude의 경우 필수 속성이 먼저, 선택 속성이 뒤에 오도록 출력 순서가 바뀌고 enum 값의 대소문자가 미묘하게 달라질 수 있어, 순서에 의존하지 말고 enum은 대소문자를 무시하고 비교하라는 안내도 있다.

추론 품질도 따져야 한다. 2024년 「Let Me Speak Freely?」 연구는 출력 형식을 엄격하게 제한할수록 수학 같은 추론 과제의 성능이 떨어지는 경향을 보고했다. 복잡한 판단이 필요한 작업이라면 모델이 먼저 자유롭게 생각하게 한 뒤 최종 결과만 스키마로 받거나, 짧은 근거 필드를 답 필드보다 앞에 두는 식으로 설계하는 게 좋다.
