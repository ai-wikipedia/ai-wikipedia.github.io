에포트 컨트롤

Effort Control / Reasoning Effort

에포트 컨트롤은 추론 모델이 답하기 전에 얼마나 생각할지를 요청 단위로 정하는 설정이다. 쉬운 요청은 빠르고 싸게 처리하고, 어려운 문제에는 토큰을 더 써서 정확도를 높이려고 쓴다.

생각하는 양을 고르는 다이얼

에포트 컨트롤(Effort Control, Reasoning Effort)은 추론 모델에게 "이번 질문엔 얼마나 깊게 생각해"라고 정해 주는 요청 단위 설정이다. 추론 모델은 최종 답을 내기 전에 사용자에게 보이지 않는 추론 토큰을 먼저 만든다. 사람에 비유하면 문제를 풀기 전 연습장에 끄적이는 과정이다. 날씨를 묻는 질문에 연습장 몇 장을 채울 필요는 없지만, 까다로운 알고리즘 버그를 잡을 때는 오래 붙잡고 있어야 답이 나온다. 에포트는 이 연습장을 얼마나 쓸지 정하는 손잡이다. 낮게 두면 답이 빨리 나오고 비용도 적게 들고, 높이면 응답이 느리고 토큰을 더 쓰는 대신 여러 단계를 거치는 추론을 더 꼼꼼히 한다.

온도(temperature)와 헷갈리기 쉽지만 다른 설정이다. 온도는 다음 토큰을 고를 때 얼마나 무작위로 뽑을지를 정하고, 에포트는 답을 내기 전에 내부적으로 얼마나 일할지를 정한다. 일부 추론 모델은 샘플링 파라미터를 아예 무시해서, 이런 모델에서는 에포트가 사실상 유일하게 동작을 조절할 수 있는 설정이다.

API에서 실제로 만지는 값

OpenAI API에서는 reasoning.effort 파라미터를 쓴다. 허용되는 값은 모델마다 다른데 none, minimal, low, medium, high, xhigh, max 중 일부를 받는다. GPT-5.6은 값을 생략하면 medium으로 동작한다. 표준 모드와 pro 모드를 고르는 추론 모드와 에포트는 서로 별개라서, pro 모드 안에서도 에포트를 따로 정한다. Claude API에서도 effort를 다섯 단계로 지정한다. 기본값은 모델마다 다르다. Claude Opus 5까지는 기본값이 high였지만 Claude Opus 5.5와 Haiku 5.5는 medium이어서, 같은 요청을 모델만 바꿔 보내면 한 단계 낮은 에포트로 실행된다.

실제로 쓸 때는 작업 성격에 맞춰 값을 고른다. Anthropic 문서는 에이전트 코딩을 포함한 대부분의 작업을 medium으로 시작하고, 채팅이나 짧은 도구 호출, 대량으로 처리하는 단순 요청에는 가장 싸고 빠른 low를 쓰라고 권한다. 다만 긴 에이전트 프롬프트를 low로 돌리면 모델이 검색을 건너뛰거나 일찍 멈추거나 검증 단계를 생략할 가능성이 커진다. 그래서 이전 모델에서 쓰던 설정을 그대로 옮기지 말고 자기 평가 세트에서 에포트별로 결과를 비교해 보라는 게 공식 권고다. 높은 에포트를 쓸 때는 추론 토큰이 많이 나오므로 max_tokens를 넉넉히 잡아야 한다.

문자열 하나 뒤에 숨은 훈련

low, medium, high는 모델이 실행 중에 알아서 바꾸는 성격이 아니다. 포스트 트레이닝 단계에서 미리 학습시켜 둔 동작이고, 추론할 때는 시스템 프롬프트 같은 지시로 그 동작을 불러낼 뿐이다. 그래서 아무 모델에나 "적게 생각해"라고 써 준다고 같은 효과가 나지 않는다. Sebastian Raschka는 이런 동작을 만드는 방법으로 두 가지를 정리했다. 하나는 에포트 수준별로 길이가 다른 추론 예시를 지도 학습(SFT)시키는 방식이고, 다른 하나는 강화학습에서 토큰 비용을 다르게 매기는 방식이다. 후자는 보상을 대략 "과제 보상 − λ(e) × 토큰 수" 꼴로 설계한다. 낮은 에포트에서는 토큰당 벌점 λ를 크게 줘서 짧게 생각하도록 유도하고, 높은 에포트에서는 벌점을 작게 줘서 길게 생각해도 되게 한다.

NeurIPS 2025에 실린 E1 연구도 비슷한 방향이다. 사용자가 "2,000토큰만 써"처럼 절대 토큰 수를 지정하는 방식은 문제 난이도를 미리 알아야 한다는 약점이 있다. E1은 대신 상대적인 에포트 값을 프롬프트에 넣고, 에포트에 따라 달라지는 보상 함수로 GRPO 같은 표준 강화학습을 돌린다. 학습이 끝나면 에포트를 올릴수록 성능과 생성 토큰 수가 함께 늘고, 최대 에포트에서도 문제 난이도에 맞춰 토큰 양을 조절했다. 기반 모델과 비교하면 성능은 유지하거나 높이면서 추론 길이를 약 3분의 1로 줄였다고 보고했다.

높이면 다 좋아지는 건 아니다

에포트를 높여서 얻는 건 어려운 문제에서의 정확도이고, 쉬운 문제에서는 얻는 게 거의 없다. 그런데도 비용과 지연 시간은 그대로 늘어나므로 모든 요청을 high로 두는 건 손해다. 최근 모델은 같은 에포트 안에서도 쉬운 작업엔 토큰을 덜 쓰고 어려운 작업엔 더 쓰도록 적응적으로 추론하지만, 그렇다고 설정을 고민할 필요가 없어지지는 않는다. 또 에포트는 보이지 않는 생각의 양을 조절할 뿐 보이는 답변 길이를 조절하는 장치가 아니다. Claude Opus 5에서는 에포트를 낮춰도 응답이 확실히 짧아지지 않아서, 답을 짧게 받고 싶으면 프롬프트로 길이를 지시해야 한다. Opus 5에서는 xhigh나 max 에포트로 요청하면서 thinking을 끄면 400 오류가 난다. 값 이름과 조합 규칙이 제공사와 모델마다 다르고, 어떤 곳은 이름 붙은 단계 대신 생각 토큰 예산을 직접 받기도 하므로, 정확한 값은 그때그때 해당 API 문서를 확인하는 게 안전하다.
