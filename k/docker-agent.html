Docker Agent

Docker Agent는 역할이 정해진 AI 에이전트 여러 개를 YAML 파일로 정의하고 `docker agent` 명령으로 실행하는 Docker의 오픈소스 프레임워크다. 코드를 짜지 않고도 에이전트 팀을 구성하고, 컨테이너 이미지처럼 레지스트리로 공유할 수 있다.

만능 비서 하나 대신 전문가 팀을 꾸리는 도구

Docker Agent는 Docker가 만든 오픈소스 AI 에이전트 빌더이자 런타임이다. 핵심 아이디어는 모델 하나에 모든 일을 시키지 말고, 역할이 다른 에이전트 여러 개를 팀으로 묶자는 것이다. 버그 하나를 잡는 상황을 떠올려 보면 쉽다. 한 에이전트가 원인을 조사하고 코드를 고치고 테스트까지 다 맡으면 계속 머리를 바꿔 가며 일해야 한다. 사람 팀이라면 조사 담당과 수정 담당을 나눌 것이다. Docker Agent는 이 분업을 설정 파일 하나로 표현하게 해 주고, 에이전트 사이의 조율은 프레임워크가 알아서 처리한다.

원래 이름은 cagent였다. Docker Desktop 4.49부터 4.62까지는 cagent라는 이름으로 들어 있었고, 4.63부터 Docker Agent로 이름이 바뀌어 기본 탑재됐다. Go로 작성됐고 docker CLI 플러그인 형태라서 docker agent로 실행한다. 헷갈리기 쉬운 것이 Gordon인데, Gordon(docker ai)은 Docker가 직접 만든 내장 AI 비서이고 Docker Agent는 개발자가 자기 에이전트 팀을 만들어 돌리는 프레임워크라는 점에서 다르다. Datadog이나 Azure Pipelines의 "Docker 에이전트"처럼 컨테이너 안에서 돌아가는 모니터링·CI 에이전트와도 별개다.

YAML 한 장으로 팀을 짜는 방법

에이전트마다 사용할 모델, 설명, 지침(instruction), 쓸 수 있는 도구를 YAML에 적는다. 특정 LLM 업체에 묶이지 않아서 여러 클라우드 모델 제공업체와 로컬 모델을 섞어 쓸 수 있다. 공식 문서의 예시는 디버깅용 2인 팀이다. 루트 에이전트가 문제를 조사하고 설명하다가, 원인을 이해하면 fixer 에이전트에게 구현을 넘긴다. 각 에이전트는 자기 전문 영역에만 집중하고, 작업 위임은 설정에 적힌 협업 구조대로 일어난다.

실제 사용 흐름은 짧다. 처음이라면 docker agent new로 대화하면서 에이전트를 만들고, 직접 쓴 설정은 docker agent run agent.yaml로 터미널에서 돌린다. Docker Desktop이 없으면 brew install docker-agent로 설치한 뒤 바이너리를 ~/.docker/cli-plugins/에 연결하면 같은 명령을 쓸 수 있다.

도구, 검색, 그리고 이미지처럼 배포하기

에이전트가 할 수 있는 일은 연결한 도구에 달려 있다. Docker Agent는 내장 도구 외에 로컬·원격·Docker 기반 MCP 서버를 붙일 수 있어서, 예를 들어 조사 담당 에이전트에게는 이슈 트래커를 읽는 MCP 서버만 주고 수정 담당에게는 파일 편집 도구를 주는 식으로 권한을 나눠 설계할 수 있다. 생각 정리, 할 일 목록, 메모리 관리용 도구도 기본으로 제공되고, 문서 검색이 필요하면 BM25, 임베딩, 하이브리드 검색에 재순위화까지 지원하는 RAG를 설정으로 켤 수 있다.

Docker다운 부분은 배포 방식이다. 에이전트 설정을 버전 관리하고 OCI 레지스트리에 올려 공유할 수 있어서, 팀원은 docker agent run myorg/agent:tag처럼 컨테이너 이미지를 받듯 에이전트를 받아 실행한다. 사내에서 다듬은 코드 리뷰 에이전트 팀을 레지스트리에 올려 두면 다른 개발자가 같은 구성을 그대로 재현할 수 있다는 얘기다. 커뮤니티에서는 에이전트 연구에서 다른 사람이 실험을 똑같이 재현하거나 LLM의 변동성 때문에 실험을 반복해야 할 때 이 점이 유용하다는 의견도 나왔다.

샌드박스와 함께 쓸 때, 그리고 남는 의문

에이전트에게 셸과 파일 접근을 주면 호스트가 망가질 위험이 생긴다. 그래서 Docker Agent는 선택적으로 격리된 VM 샌드박스에서 실행할 수 있다. Docker Sandboxes는 Claude Code, Gemini, Codex, Copilot, Kiro와 함께 Docker Agent를 기본 지원 에이전트로 넣었고, docker sandbox run agent ~/path/to/workspace로 바로 띄운다. 이 샌드박스는 커널을 공유하는 일반 컨테이너가 아니라 자체 커널과 전용 Docker Engine을 가진 마이크로VM이라서, 에이전트가 안에서 컨테이너를 빌드하고 실행해도 호스트까지 닿지 않는다. 다만 이 기능은 아직 실험 단계라 Docker Desktop 버전 사이에 호환이 깨질 수 있고, 마이크로VM 방식은 macOS와 Windows에서만 지원된다.

반응이 마냥 호의적이지만은 않다. 에이전트 하네스가 예전 자바스크립트 프레임워크처럼 너도나도 하나씩 내놓는 물건이 됐다는 냉소가 있고, 이미 modal.com이나 e2b 같은 격리 실행 환경이 있는데 이 추상화가 왜 필요하냐는 지적도 있다. Docker 하네스 자체가 필요 없고 격리만 원한다면 샌드박스 위에 Claude Code나 Codex를 직접 올려도 된다. 결국 Docker Agent의 강점은 YAML로 선언하는 팀 구성과 레지스트리 배포에 있으니, 이 두 가지가 필요한지를 기준으로 고르는 게 좋다.
