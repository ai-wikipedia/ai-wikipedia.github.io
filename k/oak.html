오크

Oak (Agent-Native Version Control)

오크(Oak)는 AI 코딩 에이전트가 작업하는 방식에 맞춰 새로 설계한 버전 관리 시스템이다. 커밋 대신 세션을 작업 단위로 삼고, 전체 클론 없이 파일을 필요할 때만 가져오는 지연 마운트를 써서 에이전트 여러 개가 한 저장소에서 빠르게 병렬로 작업하게 해 준다.

사람 손에 맞춰진 Git, 에이전트에게는 왜 불편한가

오크(Oak)는 AI 코딩 에이전트를 위해 처음부터 다시 만든 버전 관리 시스템이다. Git은 사람이 파일을 하나씩 고치고, 의미 있는 단위마다 메시지를 붙여 커밋하는 순차적인 작업 흐름을 전제로 만들어졌다. 그런데 요즘은 에이전트 여러 개가 한 저장소에서 동시에 다른 작업을 하고, 수십 번씩 중간 상태를 저장했다가 되돌리기도 한다. 이런 상황에서 Git을 쓰면 시작부터 저장소 전체를 클론해야 하고(큰 저장소면 몇 분씩 걸린다), 병렬 작업을 하려면 하나의 .git을 공유하는 git worktree에 기대야 하며, 저장할 때마다 커밋 메시지를 써야 한다. 오크는 바로 이 지점을 겨냥한다. 핵심 아이디어는 한 문장으로 정리된다. 에이전트에게 작업의 단위는 커밋이 아니라 세션이라는 것이다.

세션, 지연 마운트, 메시지 없는 체크포인트

오크에서는 작업 하나마다 브랜치가 생기고, 에이전트마다 지연 마운트(lazy mount)가 붙는다. 지연 마운트는 저장소를 통째로 내려받지 않고 작업 트리를 먼저 띄운 뒤, 에이전트가 어떤 파일을 처음 읽는 순간에 그 파일을 스트리밍해 오는 방식이다. 도서관 책을 전부 빌려 집에 쌓아 두는 대신, 필요한 페이지를 펼칠 때마다 가져다주는 셈이다. 덕분에 병렬 작업이 필요하면 작업마다 마운트를 하나씩 따로 띄우면 되고, 각 마운트는 자기 브랜치를 가진다. 저장은 메시지가 필요 없는 체크포인트로 남기고, 작업이 끝나면 작업 설명이 스쿼시 커밋의 메시지가 된다. 에이전트가 중간중간 커밋 메시지를 짜내느라 토큰을 쓰지 않아도 되고, 최종 이력은 깔끔하게 남는다.

개발자가 쓰는 장면은 단순하다. curl -fsSL oak.space/install | sh로 설치하고 oak login, oak init을 실행한 뒤 에이전트에게 "Git 대신 Oak를 써라"라고 지시하면 된다. 모델이나 IDE를 바꿀 필요가 없다는 것이 제작진의 설명이다. 예를 들어 Claude Code 같은 에이전트에게 버그 수정 세 건을 동시에 맡기면, 각 작업이 자기 마운트와 브랜치에서 돌아가므로 서로의 작업 트리를 건드리지 않는다. 모든 명령이 --json 출력과 타입이 정해진 종료 코드를 지원하기 때문에, 에이전트가 사람용 텍스트 출력을 해석하지 않고 결과를 그대로 파싱해 다음 행동을 정할 수 있다는 점도 에이전트 친화적인 설계다.

내부 구조와 성능 주장

오크는 Rust로 작성됐고, 라이브러리(oakvcs-core)와 명령줄 클라이언트(oak) 두 부분으로 나뉜다. 라이브러리는 BLAKE3 기반 콘텐츠 해싱, 콘텐츠 정의 청킹, diff와 merge 알고리즘, 그리고 Blob·Manifest·Commit·Tree 같은 핵심 데이터 모델을 담당한다. 콘텐츠 정의 청킹(fastcdc)은 파일을 내용 기준으로 조각내 버전 사이에서 겹치는 조각을 중복 저장하지 않는 방식이라, Git에서 LFS를 따로 설정해야 했던 대용량 파일도 별도 구성 없이 다룬다. 이미지나 모델 산출물처럼 에이전트가 만들어 내는 바이너리가 많아질수록 의미가 커지는 부분이다. 제작진 벤치마크로는 대형 저장소에서 스냅샷과 상태 확인이 Git보다 최대 95% 빠르다고 한다. 현재 v0.99.0 공개 베타이며 Apache-2.0 라이선스로 공개됐고, Zach Geier가 만들고 Adam Morse가 제품과 시각 디자인을 맡았다. 사용자 코드를 학습에 쓰지 않는다는 점도 명시하고 있다.

Git을 대체할까, Git 위에 얹힐까

오크는 아직 초기 단계의 실험적인 선택지다. 성능 수치는 제작진이 직접 잰 벤치마크이고, 팀 전체가 Git과 GitHub 중심 흐름에서 벗어나는 데는 리뷰 도구, CI, 기존 이력과의 호환 같은 전환 비용이 따른다. 비평 쪽에서도 에이전트가 세션을 일급 객체로 다루는 버전 관리 경험이 필요하다는 문제의식에는 동의하지만, 현실적인 경로는 Git을 바닥에 두고 그 위에 작업 공간, 작업 기록, 정리, 리뷰, 정책 같은 에이전트 전용 계층을 얹는 쪽일 가능성이 높다고 본다. 그래서 오크는 당장 도입할 표준이라기보다, 앞으로 코드 수정 대부분이 에이전트에게서 나온다면 버전 관리가 어떤 모습이어야 하는지를 구체적인 도구로 보여 주는 시도로 보는 편이 정확하다. 병렬 에이전트 작업에서 클론 시간이나 worktree 충돌 때문에 고생하고 있다면 사이드 프로젝트에서 먼저 써 보며 판단하는 것이 무난하다.
