미스트랄 미디엄 3.5

Mistral Medium 3.5

프랑스 Mistral AI가 내놓은 첫 플래그십 통합 모델로, 지시 따르기·추론·코딩을 하나의 모델에 합쳐 에이전트 작업과 코딩에 강하다.

세 모델을 하나로 합친 플래그십

Mistral Medium 3.5는 프랑스 Mistral AI가 2026년 4월 말 공개한 모델이다. 그동안 Mistral은 대화용 Medium, 추론 특화 Magistral, 코딩 특화 Devstral을 따로 내놨고, 개발자는 작업마다 모델을 바꿔 끼워야 했다. Medium 3.5는 지시 따르기, 추론, 코딩을 한 벌의 가중치에 합쳤다. 공개와 함께 Mistral의 챗봇 Le Chat에서 Medium 3.1과 Magistral을 대신하는 기본 모델이 됐고, 코딩 에이전트 Vibe CLI의 기본 모델도 Devstral 2에서 이 모델로 바뀌었다.

요즘 대형 모델 대부분이 일부 전문가만 켜는 MoE 구조인 것과 달리, Medium 3.5는 1,280억 파라미터를 토큰마다 전부 쓰는 dense 모델이다. 문맥은 25만 6천 토큰이고, 크기와 비율이 제각각인 이미지를 처리하도록 처음부터 새로 학습한 비전 인코더를 달아 이미지 입력도 받는다. 가중치는 Hugging Face에 공개됐는데, 이전 Mistral 모델들의 Apache 2.0이 아니라 수정된 MIT 라이선스다. 상업적 사용은 허용하지만 매출이 아주 큰 기업에는 예외 조건이 붙으므로 대기업이라면 약관부터 확인해야 한다.

추론을 켜고 끄는 한 모델

합친 모델의 장점은 요청마다 생각의 깊이를 바꿀 수 있다는 점이다. reasoning_effort를 none으로 주면 곧바로 답하고, high로 주면 추론 과정을 거친다. Mistral은 복잡한 질문과 에이전트 작업에는 high를 권한다. 권장 샘플링 값도 모드마다 다르다. high에서는 temperature 0.7, top_p 0.95를, none에서는 작업에 따라 0.0에서 0.7 사이의 낮은 temperature를 쓰라고 안내한다. 한 서비스 안에서 빠른 채팅 응답과 긴 코딩 작업을 같은 모델로 처리하고, 요청 성격에 따라 이 값만 바꾸면 되는 구조다. 함수 호출과 JSON 출력도 기본으로 지원한다.

직접 띄우기와 Vibe 원격 에이전트

API 가격은 입력 100만 토큰당 1.5달러, 출력 7.5달러다. 직접 서빙한다면 vLLM이 권장 경로다. 공식 예시는 vllm serve mistralai/Mistral-Medium-3.5-128B에 GPU 8장 텐서 병렬을 걸고, Mistral 전용 도구 호출 파서와 추론 파서를 켜는 구성이다. Mistral은 최소 GPU 4장으로도 자체 호스팅이 가능하다고 밝혔지만, 잘 갖춘 데이터센터가 아니면 현실적으로 쉽지 않다는 평가가 많다. FP8 가중치도 함께 제공된다.

이 모델이 실제로 많이 쓰이는 곳은 Mistral의 코딩 에이전트 Vibe다. Vibe의 원격 에이전트 기능은 코딩 세션을 노트북이 아니라 클라우드 샌드박스에서 비동기로, 여러 개를 동시에 돌린다. 로컬 CLI에서 시작한 세션을 대화 기록과 승인 상태째로 클라우드로 옮길 수 있고, 작업이 끝나면 GitHub 풀 리퀘스트를 열고 알림을 보낸다. 리팩토링, 테스트 생성, 의존성 업그레이드, CI 실패 조사처럼 오래 걸리지만 감독이 덜 필요한 일을 던져 두기 좋다. 이슈는 Linear나 Jira에서, 장애는 Sentry에서 받아 오고 결과는 Slack이나 Teams로 보고하도록 연결할 수도 있다. Pro, Team, Enterprise 요금제에서 쓸 수 있다.

같은 모델은 Le Chat의 새 Work 모드도 돌린다. 메일, 메시지, 캘린더를 오가며 회의 준비 자료를 만들거나 받은편지함을 정리하고 답장 초안을 쓰는 식의 여러 단계 작업을, 도구를 동시에 여러 개 호출하며 끝까지 처리한다. 메시지 전송이나 데이터 수정처럼 민감한 동작은 사용자의 명시적 승인을 받고, 어떤 도구를 왜 불렀는지 모두 화면에 보여준다.

고를 때 따질 것

Mistral이 발표한 SWE-bench Verified 점수는 77.6%로 Devstral 2와 Qwen3.5 397B보다 높다. 다만 독립 기관의 검증 수치가 아니라 회사 자체 발표다. 구조적인 약점도 분명하다. dense 128B는 토큰마다 전체 가중치를 계산해야 하므로, 활성 파라미터가 수백억 개 수준인 MoE 모델보다 같은 하드웨어에서 추론 비용이 더 든다. 초기 Transformers 설정에는 긴 문맥 성능을 떨어뜨리는 문제가 있다가 수정됐으니, 그 전에 만들어진 GGUF 변환본은 피하는 게 좋다. 유럽 기업이 만든 오픈 웨이트 모델이라는 점, 그리고 채팅부터 코딩 에이전트까지 하나의 모델로 통일할 수 있다는 점이 이 모델을 고르는 가장 큰 이유다.
