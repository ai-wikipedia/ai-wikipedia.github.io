AI 코드 리뷰

AI Code Review

AI가 PR의 변경 내용(diff)을 읽고 버그, 보안 취약점, 성능·스타일 문제를 코멘트로 짚어 주는 기술이다. 기계적인 문제는 AI가 먼저 거르고, 사람 리뷰어는 설계와 비즈니스 로직에 집중하도록 일을 나눌 때 쓴다.

구분잘 잡는 것한계
린터·정적 분석정해진 규칙 위반규칙 밖의 문제는 못 봄
AI 코드 리뷰로직 실수, 인증 누락, SQL 인젝션 같은 맥락 있는 문제가끔 틀린 지적을 함
사람 리뷰설계, 요구사항에 맞는지시간이 오래 걸림

설치형 도구와 직접 구성, 두 가지 방법

가장 쉬운 방법은 CodeRabbit, GitHub Copilot Code Review처럼 GitHub에 바로 붙는 도구를 쓰는 것이다. 저장소에 연결해 두면 PR이 열릴 때마다 변경 요약과 줄 단위 코멘트가 달린다. Cursor처럼 에디터 안에서 커밋하기 전에 리뷰를 받는 방식도 있다.

직접 만들려면 GitHub Actions에서 PR 이벤트가 들어올 때 diff를 Claude API로 보내고, 응답을 PR 코멘트로 남기게 구성한다. 처음 설정하는 데 시간이 들지만 프롬프트와 검사 범위를 마음대로 정할 수 있다.

방식장점이럴 때 고른다
설치형 도구연결만 하면 바로 씀빠르게 도입하고 싶을 때
직접 구성 (Actions + API)프롬프트·범위를 자유롭게 정함사내 규칙이 많거나 비용을 세밀하게 관리할 때

팀 규칙을 알려줘야 지적이 정확해진다

아무 설정 없이 쓰면 누구에게나 할 법한 일반적인 지적만 나온다. 팀 코딩 컨벤션, 자주 나는 실수, 꼭 확인할 항목(인증 체크, 입력 검증 등)을 시스템 프롬프트나 도구 설정에 적어 두면 맥락에 맞는 코멘트가 나온다. 자동 생성 파일이나 lock 파일은 검사 대상에서 빼야 쓸데없는 코멘트가 줄어든다.

참고 의견으로 받고, 머지는 사람이 정한다

AI는 문제없는 코드를 문제라고 하거나, diff 밖의 코드와 얽힌 버그를 놓치기도 한다. 그래서 AI 코멘트를 전부 따르기보다 참고 의견으로 받고, 최종 승인은 사람이 하는 팀 문화가 중요하다. AI가 짠 코드가 늘면서 리뷰할 양도 많아졌으니, AI 리뷰는 사람 리뷰를 대신하는 게 아니라 앞에서 한 번 걸러 주는 역할로 두는 게 좋다.

외부 서비스를 쓰면 코드가 그 서비스로 전송된다. 민감한 저장소라면 도입 전에 보안 정책부터 확인해야 한다.

PR의 첫 번째 리뷰어로 둔다

가장 흔한 방식은 PR이 열리면 AI가 먼저 변경 요약과 줄 단위 코멘트를 달고, 사람은 그걸 참고하면서 설계와 요구사항을 보는 것이다. 올리기 전에 에디터에서 미리 리뷰를 받는 쓰임도 많다.

어디서어떻게 쓰나
GitHub PR설치형 도구나 Actions로 연결해 PR마다 변경 요약과 줄 단위 코멘트를 자동으로 받는다
에디터 (커밋 전)올리기 전에 리뷰를 받아 기본적인 실수를 미리 고친다
AI가 짠 코드 점검코딩 에이전트가 만든 큰 변경을 사람이 보기 전에 한 번 걸러 리뷰 부담을 줄인다
보안 항목 확인인증 누락·입력 검증처럼 꼭 볼 항목을 프롬프트에 적어 두고 PR마다 반복해서 확인한다
