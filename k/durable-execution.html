내구성 실행

Durable Execution

내구성 실행(Durable Execution)은 코드가 실행되는 동안 각 단계의 결과를 기록해 두고, 프로세스가 죽더라도 처음부터가 아니라 마지막으로 끝낸 단계부터 이어서 실행하게 하는 프로그래밍 방식입니다. 재시도 로직이나 상태 저장 코드를 직접 짜지 않아도 결제, 장시간 워크플로우, AI 에이전트 같은 작업을 장애가 나도 끝까지 마칠 수 있습니다.

중간에 쓰러져도 이어서 달리는 코드

내구성 실행이란 함수가 실행되는 동안 단계마다 진행 상황과 결과를 저장해 두는 방식이다. 그래서 서버가 죽거나 재시작되거나 네트워크가 끊겨도, 함수를 처음부터 다시 돌리지 않고 마지막으로 끝낸 단계부터 다시 시작한다. 게임의 세이브 포인트를 떠올리면 쉽다. 보스 앞에서 전원이 꺼져도 1스테이지부터 다시 하지 않고 마지막 세이브 지점에서 이어 한다. 예를 들어 "결제 승인 → 재고 차감 → 배송 요청 → 이메일 발송"으로 이어지는 주문 처리 코드가 재고 차감 직후에 죽었다고 하자. 그냥 다시 실행하면 결제가 두 번 될 수 있고, 아예 다시 실행하지 않으면 돈만 받고 배송은 안 된다. 그래서 개발자는 지금까지 상태 테이블을 만들고 "어디까지 했는지"를 DB에 적고 재시도 코드를 직접 짜야 했다. 내구성 실행 엔진은 이 기록과 복구를 대신 맡는다. 결제나 장바구니가 거의 모든 내구성 실행 프레임워크의 대표 예제로 쓰이는 이유가 여기 있다.

지역 변수까지 살아남는 원리

Temporal은 내구성 실행을 "실행 자체를 가상화하는 것"이라고 설명한다. 하나의 실행이 여러 프로세스에 걸쳐 이어질 수 있고, 각 프로세스는 이전과 다른 기계에서 돌아가도 된다. 현재 프로세스가 죽으면 새 프로세스에서 애플리케이션 상태를 다시 만들어 내고, 장애가 없었던 것처럼 실행을 계속한다. 그 결과 지역 변수를 포함한 모든 변수가 장애 전과 같은 값을 갖는다. 이를 위해 엔진은 각 단계의 입력과 결과를 로그로 남기고, 복구할 때는 코드를 처음부터 다시 돌리되 이미 끝난 단계는 실제로 실행하지 않고 기록된 결과를 꺼내 쓰는 리플레이 방식을 많이 쓴다. AWS Lambda 내구성 실행 SDK도 같은 구조로, DurableContext를 통해 호출한 작업마다 체크포인트가 생기고 실행마다 다른 실행이 접근할 수 없는 독립된 체크포인트 로그를 가진다. 기존 워크플로우 엔진이 YAML이나 DSL, 시각적 그래프로 흐름을 정의하게 했던 것과 달리, 내구성 실행은 일반 프로그래밍 언어로 if문과 반복문을 그대로 쓰면서 같은 신뢰성을 얻는다는 점이 다르다.

개발자가 실제로 쓰는 장면

쓰는 방식은 대체로 비슷하다. 순서대로 실행되는 평범한 함수를 작성하고, 외부 API 호출이나 DB 쓰기처럼 부작용이 있는 부분을 "단계(step)"로 감싼다. AWS Lambda 내구성 함수라면 각 단계가 자동으로 체크포인트되고, 사람의 승인처럼 오래 걸리는 대기는 최대 1년까지 실행을 멈췄다가 콜백이 오면 이어서 진행한다. 서버를 계속 띄워 둘 필요 없이 기다리는 동안 비용이 들지 않는 셈이다. AI 쪽에서는 RAG 데이터 수집 파이프라인이 대표적이다. 문서 추출, 청킹, 임베딩, 인덱싱을 단계로 나눠 두면 수천 개 문서를 처리하다 임베딩 API가 잠시 실패해도 이미 끝난 문서는 건너뛰고 실패한 지점부터 다시 시작한다. MongoDB 문서의 레퍼런스 아키텍처가 Temporal을 이 수집 파이프라인과 에이전트 워크플로우의 실행 계층으로 두는 것도 같은 이유다. 도구 호출과 모델 호출을 여러 번 오가는 리서치 에이전트에서도 모델 응답 하나하나를 단계로 기록해 두면, 중간에 배포가 일어나도 이미 비싸게 얻은 LLM 응답을 다시 요청하지 않는다. LangGraph도 같은 개념을 도입해 그래프 실행 중 주요 지점에 상태를 저장하고, 사람의 확인을 기다렸다가 멈춘 곳에서 정확히 재개하게 한다.

외부 오케스트레이터냐, 라이브러리냐

구현 방식은 크게 두 갈래다. AWS Step Functions와 Temporal 같은 1세대 시스템은 외부 오케스트레이터가 프로그램의 제어 흐름을 관리하는 "서비스" 형태다. 워크플로우와 실제 일을 하는 단계를 나누고, 별도 서버가 진행 상태를 들고 있다. 반면 DBOS는 내구성 실행을 기존 프로그램에 추가하는 오픈소스 라이브러리로 구현해 별도 인프라 없이 애플리케이션 DB에 상태를 저장하는 가벼운 방식을 주장한다. Restate처럼 자체 런타임을 둔 쪽도 있고, Microsoft는 Durable Task라는 이름으로 같은 개념을 제공한다. 어느 쪽이든 핵심 약속은 같지만, 운영할 컴포넌트 수와 지연 시간이 달라진다.

만능은 아니다

단계 실행 도중 크래시가 나면 그 단계는 다시 실행되므로, 보장되는 것은 "정확히 한 번"이 아니라 "최소 한 번"이다. 결제 API 호출 같은 단계는 멱등성 키를 붙이는 식으로 중복 실행에 대비해야 한다. 리플레이 방식은 워크플로우 코드가 결정적이어야 해서 현재 시각이나 난수를 직접 쓰면 안 되고, 실행 중인 워크플로우가 있는 상태에서 코드를 바꾸는 것도 까다롭다. 실제로 개념 검증 단계에서는 괜찮다가 로직이 복잡해지면서 학습 비용과 디버깅 부담이 커졌다는 현업 후기도 있다. 체크포인트에 저장되는 입력과 결과 데이터는 저장 비용으로 이어지므로, 큰 페이로드를 단계 결과로 그대로 넘기지 않는 설계도 필요하다.
