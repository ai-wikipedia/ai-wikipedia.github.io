Batch Inference

급하지 않은 LLM 요청을 많이 모아 한꺼번에 맡기고, 결과는 나중에 받는 방식이다. 문서 분류·대량 번역·야간 리포트처럼 바로 답이 필요 없는 대량 작업에서 비용을 줄일 때 쓴다.

한눈에 보기

모든 LLM 요청에 바로 답이 필요한 건 아니다. 수십만 건의 문서를 분류하거나 상품 설명을 번역하는 일은 몇 시간 안에만 끝나면 된다. 배치 추론은 이런 요청을 모아 한 번에 맡기는 방식이다. 기다리는 대신 요금이 온디맨드의 절반 정도로 내려간다.

항목일반 API 호출배치 API
응답바로 (초 단위)나중에 (최대 24시간)
요금기본가약 50% 할인
맞는 작업채팅, 실시간 기능대량 분류·요약·번역

왜 싸게 해 주나

응답 시간 약속이 없으니 제공사는 서버가 한가할 때 요청을 몰아서 처리해 GPU를 꽉 채워 쓸 수 있다. 그렇게 아낀 비용을 할인으로 돌려주는 구조다. 배치 요청은 보통 일반 호출과 따로 한도를 잡기 때문에, 대량 작업을 돌려도 실시간 서비스의 한도를 덜 잡아먹는다.

쓰는 순서: 모아서 제출하고, ID로 맞춘다

OpenAI와 Anthropic 모두 배치 API를 제공하고, 흐름은 비슷하다. 요청마다 내가 정한 custom_id를 붙여 한 묶음으로 제출하고, 상태를 확인하다가 끝나면 결과를 받는다.

단계할 일
1. 준비요청마다 custom_id와 프롬프트 작성
2. 제출OpenAI는 JSONL 파일 업로드 후 배치 생성, Anthropic은 요청 목록을 배치로 전송
3. 확인배치 상태를 주기적으로 조회
4. 결과JSONL 결과를 받아 custom_id로 원래 요청과 연결

결과가 제출한 순서대로 온다는 보장이 없으니 꼭 custom_id로 맞춰야 한다. 앞부분 지시문이 같은 요청이 많다면 프롬프트 캐싱과 같이 써서 비용을 더 줄일 수 있다.

쓸 때와 안 쓸 때

밤새 돌리는 데이터 파이프라인, 대규모 로그 분석, 평가용 데이터셋 채점처럼 결과를 나중에 모아 보는 일이면 배치가 낫다. 사용자가 화면 앞에서 기다리는 채팅이나 스트리밍, 앞 단계 답을 보고 다음 요청을 정하는 에이전트 루프에는 맞지 않는다.

주의할 점

묶음 안에서 일부 요청만 실패할 수 있다. 결과에서 오류난 custom_id만 골라 다시 제출하는 처리를 미리 만들어 둔다. 결과 파일은 정해진 기간만 보관되니 받는 즉시 저장하는 게 좋다. 직접 모델을 띄워 쓴다면 vLLM 같은 서빙 엔진의 오프라인 배치 모드로 같은 효과를 낼 수 있다.
