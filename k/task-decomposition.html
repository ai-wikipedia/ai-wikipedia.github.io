태스크 분해

Task Decomposition

큰 작업을 AI가 하나씩 처리하고 점검할 수 있는 작은 단계로 나누는 방법이다. 여러 단계가 얽힌 코딩·조사·문서 작업을 에이전트에게 맡길 때 가장 먼저 할 일이다.

항목한번에 맡기기나눠서 맡기기
결과 확인끝나야 알 수 있음단계마다 확인
실수했을 때처음부터 다시그 단계만 다시
빠뜨리는 일자주 생김체크리스트로 줄어듦
맞는 작업짧고 단순한 요청여러 단계가 얽힌 작업

예를 들어 "신제품 출시 마케팅 계획 세워줘"라면 "시장 분석 → 타겟 정의 → 채널 선정 → 콘텐츠 기획 → 타임라인 작성"으로 나눈다. AI는 단계마다 결과를 쌓아 가며 최종 목표까지 간다.

계획을 먼저 받고, 확인한 뒤 실행한다

가장 쉬운 방법은 실행하기 전에 계획부터 받는 것이다. "바로 고치지 말고 할 일을 단계 목록으로 먼저 보여줘"라고 하면 AI가 체크리스트를 만든다. 빠진 단계나 순서를 고친 다음 "1번부터 진행해"라고 하면 된다.

Claude Code 같은 코딩 에이전트로 큰 기능을 만들 때는 스펙 분석, 데이터 모델 설계, API 구현, 테스트 작성 순으로 할 일 목록을 만든다. 그리고 하나씩 지워 가며 진행한다. 큰 단계 안에 세부 단계를 다시 넣는 계층적 분해를 쓰면 더 큰 작업도 다룰 수 있다. API로 직접 만들 때는 단계마다 따로 호출하고, 앞 단계의 결과를 다음 호출에 입력으로 넘기면 된다.

미리 다 짤지, 하면서 정할지

나누는 방식은 크게 두 가지다. 할 일을 미리 내다볼 수 있으면 처음에 전체 계획을 세운다. 결과를 봐야 다음 할 일이 정해지는 일이면 한 단계씩 정한다.

방식방법이럴 때
처음에 다 나누기전체 계획을 세우고 순서대로 실행보고서 작성, 절차가 정해진 기능 개발
하면서 나누기단계가 끝날 때마다 결과를 보고 다음 단계를 정함버그 원인 찾기, 자료 조사
섞어 쓰기큰 틀만 먼저 정하고 세부는 진행하며 고침오래 걸리는 에이전트 작업 대부분

너무 잘게 쪼개면 오히려 손해

단계가 많아질수록 호출이 늘어 시간과 비용이 커지고, 단계 사이에서 맥락이 빠지기 쉽다. 결과가 맞는지 바로 판단할 수 있는 크기로 나누는 게 적당하다. 짧은 질문이나 한 문단 요약처럼 단순한 일은 나누지 않는 편이 낫다.

처음 세운 계획이 틀리면 뒤 단계가 줄줄이 어긋난다. 중간 결과가 예상과 다르면 계획을 다시 세우게 하자. 단계마다 무엇을 끝냈는지 적어 두면 작업이 길어져도 헤매지 않는다. 사고의 사슬(CoT)은 한 번의 답변 안에서 생각을 단계별로 풀어 쓰는 것이다. 태스크 분해는 작업 자체를 따로 실행하고 점검할 단위로 나눈다는 점이 다르다.

큰 일은 목록부터 받고 하나씩 맡긴다

가장 흔한 건 에이전트에게 긴 작업을 맡기기 전에 할 일 목록부터 받는 방식이다. 목록을 사람이 확인하고 고친 뒤, 단계마다 결과를 보면서 다음으로 넘어간다.

어디서어떻게 쓰나
코딩 에이전트큰 기능을 할 일 목록으로 만들고 구현·테스트하며 하나씩 지워 나감
자료 조사검색 → 읽기 → 정리로 나누고, 앞 결과를 보고 다음에 찾을 것을 정함
보고서·문서 작성목차를 먼저 받아 확인한 뒤 섹션별로 나눠 씀
API 자동화단계마다 따로 호출하고 앞 단계 결과를 다음 입력으로 넘김
