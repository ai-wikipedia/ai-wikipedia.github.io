프롬프팅

AI에게 원하는 답을 얻으려면 "무엇을 묻느냐"만큼 "어떻게 묻느냐"가 중요합니다. 같은 모델이라도 질문을 어떻게 설계하느냐에 따라 결과물의 품질이 몇 배씩 갈리기 때문에, 프롬프트를 다루는 기술은 하나의 독립된 분야가 됐습니다. 처음이라면 프롬프트 엔지니어링에서 전체 그림을 잡고, 모델이 단계적으로 생각하게 만드는 사고의 사슬(CoT), 모델의 기본 성격을 정하는 시스템 프롬프트로 넓혀가는 순서를 권합니다. 퓨샷·제로샷 같은 예시 제공 전략, XML 프롬프팅 같은 구조화 기법, 프롬프트를 코드처럼 버전 관리하는 프롬프트 매니지먼트까지 — 모델을 정확하게 다루기 위한 기법들을 모았습니다.
  • 감정 프롬프팅 Emotion Prompting프롬프트 끝에 "이건 정말 중요해" 같은 감정을 실은 문장 한두 개를 붙여 LLM이 더 신중하고 꼼꼼하게 답하도록 하는 기법이다. 비용 없이 바로 시도할 수 있어 코드 리뷰나 글쓰기처럼 꼼꼼함이 결과를 좌우하는 일에 써 볼 만하지만, 효과는 모델과 과제에 따라 들쭉날쭉하다.
  • 메타 프롬프트 Meta-PromptLLM에게 "이 작업에 맞는 프롬프트를 써 줘"라고 부탁하는 프롬프트를 만드는 프롬프트다. 새 챗봇·에이전트의 첫 시스템 프롬프트 초안을 빨리 얻거나 이미 쓴 프롬프트를 다듬을 때 쓰며, 사람이 직접 쓰는 방식과 자동 최적화 도구의 중간쯤에 있다.
  • 사고의 사슬 Chain-of-Thought답을 바로 내지 않고 풀이 과정을 먼저 글로 쓰게 해서 정확도를 높이는 프롬프팅 기법으로, 수학·논리·코드처럼 여러 단계를 거쳐야 하는 문제에 쓴다. 단순 사실 질문에는 효과가 거의 없고 토큰만 더 든다.
  • 셀프 컨시스턴시 Self-Consistency같은 질문을 여러 번 풀게 한 뒤 가장 많이 나온 답을 고르는 프롬프트 기법으로, 수학·논리 추론이나 분류처럼 정답이 하나로 떨어지는 문제에서 정확도를 높이고 싶을 때 쓴다. 호출 횟수만큼 비용이 더 들지만, 한 번 물어서 나온 답보다 정확도가 크게 오른다.
  • 시스템 프롬프트 System Prompt대화가 시작되기 전에 AI에게 역할, 규칙, 말투를 미리 정해 주는 지시문으로, 사용자에게는 보이지 않지만 모든 대화에 똑같이 적용되는 AI의 근무 수칙이다. 요청마다 바뀌는 사용자 메시지와 달리, 사용자가 무엇을 묻든 늘 지켜야 할 규칙을 정할 때 쓴다.
  • 역할 프롬프팅 Role PromptingLLM에게 "당신은 10년 경력의 보안 전문가입니다"처럼 역할을 줘서 그 관점과 말투로 답하게 하는 기법으로, 답의 톤·관점·집중할 부분을 정하고 싶을 때 가장 간단하게 쓴다. 다만 정답률이 오르는지는 작업마다 달라서 역할 하나로 모든 답이 좋아진다고 기대하면 안 된다.
  • 자동 프롬프트 최적화 Automatic Prompt Optimization사람이 문구를 하나씩 고치는 대신 입출력 예시와 채점 기준을 주면, 시스템이 여러 프롬프트 후보를 만들어 시험하고 점수가 가장 높은 것을 골라 주는 방식이다. 분류·추출처럼 정답을 판단할 기준이 있는 반복 작업에 쓰고, 모델을 바꿔도 다시 돌리기만 하면 된다는 점이 수동 조율과 다르다.
  • 제로샷 Zero-Shot Prompting예시 없이 지시만으로 모델에게 작업을 시키는 프롬프팅 방식으로, 평소 ChatGPT나 Claude에 질문하는 방식이 대부분 여기에 해당한다. 예시를 고를 수고가 없고 프롬프트가 짧아 비용도 적어서 새 작업은 보통 제로샷으로 먼저 시작하고, 형식이나 말투가 자꾸 어긋날 때 예시를 넣는 퓨샷으로 넘어간다.
  • 출력 포맷팅 Output FormattingLLM의 답이 JSON, 마크다운, 정해진 템플릿처럼 원하는 형식으로 나오게 하는 기법이다. 사람이 읽을 글은 프롬프트에 형식을 적어 주면 충분하다. 프로그램이 받아 처리할 데이터는 형식이 한 번만 어긋나도 파싱이 깨지므로 구조화 출력처럼 형식을 강제하는 방법을 쓴다.
  • 컨텍스트 스터핑 Context Stuffing참고 문서를 골라 넣지 않고 통째로 프롬프트에 넣어, 필요한 부분은 LLM이 스스로 찾아 쓰게 하는 방식이다. 문서가 컨텍스트 창에 들어갈 만큼 작고 자주 바뀌지 않을 때 RAG 대신 쓰는 가장 간단한 방법이다.
  • 컨텍스트 엔지니어링 Context EngineeringLLM이 답하기 전에 보는 지시문, 도구 정의, 검색 결과, 대화 이력, 작업 상태까지 무엇을, 얼마나, 언제 넣을지 설계하는 방법이다. 프롬프트 한 줄을 다듬는 데서 그치지 않고 컨텍스트 윈도우 전체를 다루며, 여러 단계를 스스로 처리하는 에이전트를 만들 때 특히 중요하다.
  • 트리 오브 쏘트 Tree of ThoughtLLM이 여러 갈래의 생각을 펼친 뒤 갈래마다 평가해 유망한 쪽만 파고들고, 막히면 되돌아가는 문제 풀이 방식이다. 한 줄로만 생각하는 Chain-of-Thought와 달리, 퍼즐이나 계획 세우기, 설계안 고르기처럼 여러 길을 시도해 봐야 하는 문제에 쓴다.
  • 퓨샷 Few-Shot Prompting프롬프트에 원하는 입력과 출력의 잘 된 예시 몇 개를 넣어, 모델이 그 패턴을 따라 답하게 만드는 기법이다. 지시문을 길게 쓰거나 파인튜닝을 하지 않고 답의 형식·어조·기준을 빠르게 맞출 때 쓰며, 모델은 그대로 두고 예시만으로 답이 달라진다.
  • 프롬프트 엔지니어링 Prompt Engineering원하는 답을 안정적으로 얻으려고 AI에게 주는 입력을 체계적으로 짜는 요령이다. 모델은 우리 머릿속을 읽지 못해서 같은 모델이라도 원하는 조건을 말로 정확히 풀어주느냐에 따라 결과가 크게 달라지므로, 요약 조건 지정·출력 형식 고정·에이전트 규칙 설정처럼 AI에게 일을 맡길 때마다 쓴다.
  • 프롬프트 체이닝 Prompt Chaining큰 작업을 여러 단계로 나눠 LLM을 여러 번 부르고, 앞 단계의 출력을 다음 단계의 입력으로 넘기는 방식이다. 한 프롬프트에 다 넣으면 모델이 헷갈리거나 일부를 빠뜨리는 작업, 처리 순서가 미리 정해진 작업에 쓴다.
  • 하네스 엔지니어링 Harness EngineeringAI 모델 자체가 아니라 모델을 감싸는 맥락·도구·가드레일·검증 구조를 설계하는 일이다. 같은 모델인데 프로젝트마다 결과가 들쭉날쭉하거나 에이전트에게 긴 작업을 맡길 때 쓰며, 프롬프트 하나가 아니라 에이전트 작업 전체를 다룬다는 점이 다르다.
  • XML 프롬프팅 XML Prompting프롬프트 안의 지시, 참고 자료, 예시, 사용자 입력을 XML 태그로 감싸 어디서부터 어디까지가 무엇인지 분명히 나누는 방법으로, 긴 자료·예시·입력이 한 프롬프트에 섞일 때 쓴다. Anthropic이 Claude 프롬프팅 가이드에서 권장하는 방식이고, 다른 LLM에서도 구분자로 흔히 쓴다.
